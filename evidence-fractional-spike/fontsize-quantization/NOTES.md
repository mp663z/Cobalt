# Font-size readback vs effective size (UNREVIEWED measurement)
Chrome 156.0.8078.47, embedded Liberation Serif (LibEmb), authored sizes 14.380..14.420 in steps of 0.001 (41 values). getComputedStyle().fontSize returns the authored value unchanged at every step (no quantization visible in readback).
Effective behaviour: the width of 100 x 'H' takes only 3 distinct values over the 41 sizes (955.078125, 956.109375, 957.15625), switching between 14.398 and 14.400 and between 14.408 and 14.410. Successive widths differ by about one 1/64 px step of font size, so the size used for advances appears snapped to a coarse grid (hypothesis: 1/64 px, with a phase not equal to the authored multiples of 1/64). The line box for line-height:1 takes 4 values (14.375, 14.390625, 14.40625, 14.421875) and switches at 14.384, 14.400, 14.416, i.e. at different authored sizes than the advance switches. So the authored->used mapping differs between the advance path and the line-height path, and is not modelled. This explains why specified line-heights missed the simple floor rule on 22 of 100 rows.
Consequence for a candidate envelope: authored sizes that are exact multiples of 1/64 px (e.g. 13.5, 14.5, 16.5, 17.75) avoid the ambiguous region in these probes only if verified by a grid test; arbitrary decimals such as 14.4 or 17.6 are outside any grounded envelope and would refuse. Not yet tested: the quantization phase at exact multiples across the 8..40 range.
