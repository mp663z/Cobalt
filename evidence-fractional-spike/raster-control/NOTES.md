# Raster layer control (UNREVIEWED measurement; no engine change)
Chrome 156.0.8078.47 headless, DPR 1, black on white, grayscale AA (0 colored-fringe pixels in a sample). Fonts embedded as data: URLs in unique families LibEmb/DejaEmb (the CSS files hold the exact bytes; they are the pinned Liberation Serif 29d12439...88ba and DejaVuSans 690243ad...0648). CDP platform fonts (raster-platform-fonts.json) report Liberation Serif / DejaVu Sans, isCustomFont true, for both embedded families on every captured H size, so binding no longer depends on file:// loading.
Measured per glyph (H, e) and per string (H x10), 7 sizes x 2 fonts, left offsets 0, 0.25, 0.5 px. Coverage = sum(255-gray)/255 over the screenshot; bbox from non-white pixels. fontdue: rasterize(f32 size) coverage sum/255, bbox w,h, xmin.
Observations (not contracts): (1) per-glyph Chrome/fontdue coverage ratio ranges 0.88..1.06 and is not constant; Chrome Liberation H coverage 24.3 at 13px, 25.5 at 13.5, then 32.6 at 14, while fontdue goes 26.8, 28.9, 31.0; so Chrome pixels do not track fontdue raster at these sizes, cause not established. (2) Chrome bbox is often 1 row shorter than fontdue (e.g. Lib 13 H 9x8 vs 10x9). (3) Horizontal offset 0.25/0.5 px changes coverage by up to ~1% and shifts bbox x0 at 0.5 for some rows, so glyph origin handling in this configuration is not sub-pixel-continuous evidence either way. (4) H x10 string coverage is within about 1% of 10x single-H coverage in Chrome on all 14 rows (the layout width of the string is not 10x the glyph advance; see earlier H10w note). Shaping/kerning/hinting not measured.
