# fontdue vs Chrome: source-grounded precision path (UNREVIEWED; sources read 2026-11-05 from main branches, versions not pinned to Chrome 156)
Sources fetched (raw GitHub, current main, NOT guaranteed identical to the Chrome 156.0.8078.47 build used in the controls):
- Blink line spacing: https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/platform/fonts/simple_font_data.cc line 176: SetLineSpacing(lroundf(ascent) + lroundf(descent) + lroundf(line_gap)). This is the rule measured as "round-sum" (875/879 and 387/387 in controls); it is Blink's own formula, so the earlier misses are in the inputs, not the sum.
- Ascent/descent inputs: https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/platform/fonts/font_metrics.cc (AscentDescentWithHacks): VDMX table path on Linux when hinting is kFull/kNormal (the three pinned faces carry no VDMX table, checked with fontTools), tiny-font path, else SkScalarRoundToScalar(ascent/descent) and, on Linux with subpixel positioning, "if descent was rounded down, borrow 1 from ascent" (descent+1, ascent-1). The metrics come from Skia (font.getMetrics), i.e. FreeType-derived, not from hhea via fontdue's float scale. So the observed Chrome ascent +1 at Liberation Serif 35.5..40 px and the 4 height misses are unexplained by fontdue's unhinted hhea scale; they are consistent with Skia/FreeType metrics differing from it, not verified.
- Skia size quantization: https://raw.githubusercontent.com/google/skia/main/src/core/SkFDot6.h: SkScalarToFDot6(x) = (int)(x * 64), truncating; https://raw.githubusercontent.com/google/skia/main/src/ports/SkFontHost_FreeType.cpp lines ~1042-1046: FT_Set_Char_Size with the 26.6 scale. So the size FreeType uses is truncated to 1/64 px. This matches the observed 1/64 plateaus in advance widths; it does not by itself explain a plateau at q+1/64 (a float-product rounding hypothesis, untested).
- Advances: same file ~1388: with linear metrics the advance is FT linearHoriAdvance (16.16) times the matrix scale, otherwise the hinted 26.6 glyph advance. Blink side: https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/platform/fonts/shaping/harfbuzz_face.cc: HarfBuzz glyph advances come from SkFontGetGlyphWidthForHarfBuzz (Skia) and are converted with SkiaScalarToHarfBuzzPosition (16.16); hb font scale = SkiaScalarToHarfBuzzPosition(size) (line ~706). Which of linear/hinted advances this build used is not established.
- fontdue 0.9.3 (registry source): advance_width = scale * hmtx advance (f32, unhinted), metrics scaled in f32 (font.rs lines 293, 487, 127-140). No 26.6 or 16.16 stage, no hinting.
Not read: where Blink converts shape-result widths to LayoutUnit (the observed word widths on the 1/64 grid suggest it), and the line-fit comparison code; the grep attempts did not locate them.
## What would close the gap (alternatives, costs; no decision taken)
1. Reproduce Skia+FreeType scaling in the model: either bind FreeType (new C dependency, build/arch decision, licensing/size review) or reimplement the FT 26.6/16.16 scaling steps in Rust. Cost: medium to large; also needs per-face hinting-mode knowledge of the Chrome build; no guarantee of exactness (HarfBuzz positions and LayoutUnit conversion still unread).
2. Keep fontdue and treat as an approximate measurement with margin-based refusal (this diagnostic). Cost: small; never exact.
3. Read the remaining Blink code (LayoutUnit conversion, line breaker fit test) to find the comparison rule; the hypotheses I ran (word/space ceil, glyph round/ceil, size lag) did not beat the baseline. Cost: bounded research, may need a Chromium checkout matching 156.
