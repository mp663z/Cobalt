# String advance accumulation vs Chrome (UNREVIEWED measurement)
Chrome 156.0.8078.47, embedded data: font families LibEmb/DejaEmb (pinned Liberation Serif and DejaVuSans), white-space:pre, line-height normal, width = getBoundingClientRect of a text span. 8 strings x 8 sizes (13,13.5,13.99,14,14.4,16,16.5,17.6) x 2 fonts x font-kerning auto/none (kern also disabled via font-feature-settings in the none case) = 256 Chrome rows; fontdue 0.9.3 per-glyph unrounded advance sum (nokern) and sum + horizontal_kern (kern) for the 128 string/size/font combos.
Result on these rows: max |Chrome nokern width - fontdue sum of advances| = 0.2023 px; max |Chrome kern-auto width - (fontdue sum + fontdue kern)| = 0.2085 px. Chrome widths are multiples of 1/64 on every row. Differences are near zero at 14, 16, 16.5 and negative up to about 0.2 at 13.99, 14.4, 17.6 on the longest strings (growing with string length), so a sum of unrounded per-glyph advances is close but not identical; the residual cause is not established (hypotheses: Chrome internal size/advance quantization, differing kern handling).
Kerning exists in Chrome by default: AVAVAVAVAV is narrower with kerning by 15-20 px (Liberation) and 7-10 px (DejaVu) than without; fontdue kerning follows within the bound above. 'The quick brown fox...' differs by 0.67-1.06 px with kerning in DejaVu, none in Liberation (no relevant pairs). The engine's behaviour regarding kerning is a separate fact that must be checked before any candidate claims string-width matching.
Not measured: shaping beyond kern/liga off, line breaking, text-align, word/letter spacing, other fonts or scripts.
